LightHouse KOReader & Connection Manual

Step-by-step connection guide and one-click copyable stack endpoints

LightHouse KOReader Plugin (Recommended)

Pre-configured

Generate a .koplugin archive from this LightHouse server. It arrives already pointed at the server origin you are using right now and already authenticated, so nothing is typed on the device. The plugin adds an on-device library browser with cover thumbnails, paging, search, one-tap EPUB download, reading status, reading statistics and Calibre ratings — laid out with the same care as this dashboard rather than as a debug tool.

1
Download the archive for this server:
Baked-in server —
2
Unpack it so the folder ends in .koplugin inside your KOReader plugins directory:
# Roadmap / Kindle
unzip lighthouse.koplugin -d /mnt/us/koreader/plugins/
# Kobo
unzip lighthouse.koplugin -d /mnt/onboard/.kobo/koreader/plugins/
You should end up with koreader/plugins/lighthouse.koplugin/main.lua. A plain unzip into the plugins folder (without -d) creates a nested folder and KOReader will not load it.
3
Restart KOReader, then open Search icon (magnifying glass) → LightHouse library (or Tools → LightHouse library): Browse library (with its Books / Authors / Series switch), Search library…, Currently reading, Highlights, Reading stats, and a per-book detail view with Download EPUB.
Library: one screen with a BOOKS | AUTHORS | SERIES switch across the top (the active segment is inverted). Books pages through the catalogue; Authors and Series read one grouping document from the server and page it on the device. Every row carries a cover in the left gutter, a bold title, a secondary line and a right-hand value column with a pixel progress bar under it. A series row names its volume count and how many are read (Isuna Hasekura · 21 books · 9 read) and puts the percentage over the fraction of volumes read in the value column (43% over 9 / 21; done over 14 / 14; — over not started). The row does not name the next unread volume — tapping it opens those books, where the volumes are listed. The footer shows the page position and the grouping, and the header's ⋮ holds refresh, paging, the other groupings, search and the connection screen.
Row layout: the title leads, a secondary line carries author and series, and the value column carries progress (a pixel bar plus the percent, or a ✓ when finished) you can read without opening the book. Rows per page follow the screen height. Section headings are marked with a left bar, and nothing relies on colour, because e-ink has none.
Square corners: every corner in the plugin is 90 degrees — menu rows, covers, buttons, dialogs, progress bars and the header's switch. The plugin draws hairlines and rects, and it builds the KOReader widgets it opens (notices, confirmations, dialogs) with the reader's corner radius zeroed for that one construction, so the rest of the reader keeps its own design.
Row width: the title and the value column share a pixel budget measured with the device's own fonts, so a row's text is shortened until it genuinely fits and the title always keeps a drawable width. The one-page rows hand that job to their own text widget, which measures and truncates in pixels; the menu rows go through the same budgeted column as before. A character count cannot bound a pixel width — 64 Burmese letters are two to three times wider than 64 Latin ones — and an overflowing row makes KOReader raise bad argument #2 to 'makeLine' and close. A build that cannot measure pixels at all falls back to a small fixed 28-glyph cap. A cover gutter too wide for a title narrows the cover first, never the row, and a row with no title shows Untitled instead of an empty line.
Cover thumbnails: each row shows the book's cover from the feed's own ?w=360 thumbnail, cached on the device for 30 days so scrolling never refetches. A book the server has no cover for is remembered too, and only when the server answers with a definitive 404 — a dropped link or a rejected key is retried on the next open instead. While a cover loads, or when a book has none, the row keeps a framed neutral placeholder — never a blank hole. Turn covers off for the fastest browsing on a slow link: LightHouse library → Show cover thumbnails.
Local progress & highlights: KOReader already writes each book's percentage, highlights and notes into the sidecar folder beside the book (<book>.sdr/metadata.<extension>.lua). The plugin reads that file directly: Highlights lists this device's quotes and notes, newest first, grouped by book (tap one to open the book at that page), and progress on every screen prefers the device's own number over the server's for books that are on this device. No connection is needed for either, nothing polls, and it is strictly read-only — the plugin never writes a sidecar and never uploads progress.
Regenerating: download again and replace koreader/plugins/lighthouse.koplugin. Do this after changing the server address or the API key.
Which server URL: the archive always targets the origin this page is served from. Download from the LAN address to get a LAN plugin, or from the WAN address to get a WAN plugin. An https:// origin uses KOReader's TLS transport; a build without TLS reports it plainly and the LAN http:// address still works.
Slow connections: the plugin follows up to 5 redirects and reads its timeouts from lighthouse_config.lua (90s catalog, 300s download by default), so a first catalog page over slow Wi-Fi still loads. Cover downloads are capped per page (a few seconds and at most a dozen images), and no single cover request is allowed to outlive that budget, so a slow link degrades to placeholders instead of a stalled catalog.
Devices that cannot take a plugin: the manual OPDS + KOSync setup in the other tabs still works and is unchanged.
Reading stats is one page: it reads /api/kosync/stats once per open (no polling, no background work) and draws everything without scrolling or paging — the four-cell headline strip (total hours, streak, today, this week), the library and year bands side by side, up to three currently-reading rows with a pixel bar and percent, the compact 52-week activity grid (one rect per day, weeks as columns), up to three recent sessions, and one footer line (LightHouse … 32 min on an average day · detail on web). Any section the server did not send is left out entirely rather than shown as zero or a placeholder.
Scope: besides the OPDS catalog, KOSync progress and statistics, the library's Authors and Series groupings read one document from /api/library/groups?by=series|author (volume and read counts), so it keeps working when the server is updated. If your server predates that endpoint, the Books view still works and the grouping switch reports the failure with a retry.
When something fails: a failed request opens a real screen that says what failed in one line, then what to do about it, then Try again. An empty library, an empty search and an empty shelf each say so and offer the next step instead of looking broken.

6 Firecrawl On-Demand Web Article Scraper
On-Demand
Articles submitted via Web Uploader or Telegram Bot leverage the self-hosted Firecrawl cluster with an on-demand lifecycle to conserve host RAM:
• Wake on Demand: LightHouse automatically wakes Firecrawl containers via docker compose start in ~2.5s when an article ingestion request arrives.
• Auto-Sleep Idle Timer: After 15 minutes of inactivity without new scrapes, containers automatically shut down (docker compose stop), immediately releasing ~2.5 GB RAM back to macOS.
• Environment Configuration: Supported .env options: FIRECRAWL_PORT (3002), FIRECRAWL_URL, FIRECRAWL_COMPOSE_DIR, FIRECRAWL_IDLE_TIMEOUT_MS (900000ms), FIRECRAWL_ENABLED (true), FIRECRAWL_ACTIVITY_DIR, and FIRECRAWL_API_KEY.
• Fail-Open Fallback: If Docker or Firecrawl is offline, article ingestion seamlessly falls back to direct browser fetch and Jina Reader.
• Async Queue & Polling: Web and API article ingestion supports asynchronous execution via POST /api/ingest-url with { "async": true }, returning an immediate { success: true, jobId, status: "queued" } to eliminate reverse proxy gateway timeouts, polled in real time via GET /api/jobs/:id.
• Batch Multi-Link Reading Lists: Ingest reading lists and multi-article queues via the Web Uploader (#urlModal) or Telegram bot. Processes multiple URLs sequentially with real-time visual progress (Ingesting link X of Y), individual job polling, and an itemized completion summary.
• CLI Control: Manage cluster state manually via bin/lighthouse firecrawl status|up|down.

Metadata Providers & Sidecar Protocol

Pluggable

Enrichment sources are registered providers, not hard-coded scrapers. The built-ins (RanobeDB, AniList, Bangumi, Google Books, OpenLibrary, MangaDex) are the first entries in the registry; any other source — Douban, a private catalog, a RanobeDB mirror — can be added as configuration only by running a small HTTP sidecar beside the server.

1. Inspect what is registered
/api/metadata/providers
Returns every provider with its id, kind (builtin or sidecar), fields, categories, priority, and the capability flags, plus the category routing table.
2. Point LightHouse at a sidecar
Create data/metadata-providers.json (or set LIGHTHOUSE_METADATA_PROVIDERS to the same JSON inline), then restart the uploader. 
{
  "providers": [
    {
      "id": "douban",
      "label": "Douban",
      "endpoint": "http://127.0.0.1:8099",
      "priority": 60,
      "categories": ["general_book", "other"],
      "fields": ["title", "authors", "synopsis", "cover", "tags"]
    }
  ]
}
LIGHTHOUSE_METADATA_PROVIDERS_OFF=1 disables all sidecars without removing the config. Sidecar endpoints are exact host:port allowlist entries for the SSRF guard, so loopback and LAN sidecars work while user-supplied URLs stay blocked.
3. The sidecar speaks three JSON routes
GET /manifest → { id, label, fields, categories, priority, protocol }
GET /search?q=&category=&volume=&author= → { results: [...] }
GET /book/{id} → { book: {...} }
Each result carries title (required), authors, synopsis, coverUrl, tags, series, volume, and an optional confidence (0–1, defaults to 0.78). A failing or offline sidecar is ignored — built-ins keep working.
Overwrite protection is unchanged for every provider
Volume conflicts still demote a candidate to confidence 0, a numbered volume still keeps its title when the candidate volume differs or is missing, and an existing cover is still never replaced across a volume mismatch. A sidecar cannot widen what gets written over your library.

Scoped API Keys (Least Privilege)

READING_SCOPED_KEYS

READING_API_KEY is the master key: it always grants full access and keeps every existing WAN client, KOReader plugin, and integration working. Add read-only or limited automation keys on top of it without ever handing out the master key.

Configuration (compact, in .env):
READING_SCOPED_KEYS="koreader-sync=ro-secret:read;ci-writer=rw-secret:write"
JSON is also accepted: {"ci":{"key":"ro-secret","scopes":["read"]}}
1
Scopes: read < write < admin. write implies read. admin is only needed for host-wide routes (/api/backup, /api/ssd, /api/system).
2
Per-resource limits: qualify a scope to one API area, e.g. books:read or kosync:write, so a key cannot touch anything else.
3
Read-only behaviour: allowed on reads (/api/books, /api/annotations, /api/kosync/*, OPDS) and refused with HTTP 403 on uploads, ingestions, updates, and deletes. Unknown or revoked keys get HTTP 401.
4
Transports: Authorization: Bearer <key>, X-API-Key: <key>, or a session cookie. Query-string credentials are always rejected. Never reuse the master key as a scoped key.
5
Verify a key: curl -H "Authorization: Bearer <key>" -X POST https://reading-sg.wavypremium.xyz:8443/api/auth/session reports the key name and its scopes without ever echoing the secret.

External SSD Whole-Library Backup

Incremental Mirror

Backs up the entire active Calibre library (EPUBs, covers, author directories) and takes atomic hot SQLite snapshots (metadata.db, cache.db, koreader-sync.db, manga.db) with SHA256 verification and auto-scheduling.

CLI Commands:
bin/lighthouse backup-ssd
bin/lighthouse backup-ssd status
bin/lighthouse backup-ssd set-time 03:00
• Scheduler Status: bin/lighthouse status reports LaunchAgent state accurately as Loaded (Idle), Disabled, or Missing plist without mistaking idle scheduled agents for dead processes.
